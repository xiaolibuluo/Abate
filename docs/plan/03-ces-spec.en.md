# Abate L2 CES Specification Layer Plan — Four Modules in Full Detail

- Document ID: PLAN-03　Status: Effective　Upstream: PLAN-00
- Covered modules: CES-SCHEMA / CES-PARSE / CES-VALID / CES-TCK

> **Design-target statement (mandatory for C-class translations)**: This document is a planning document. All `100%` / "pass" / "met"-style statements below are **Design targets / Acceptance targets**, **not measured results**. No claim is made that any target has been achieved.

Common constraints (observed jointly by the four modules):

1. CES (Chaos Experiment Specification) is an open, vendor-neutral specification: the specification text evolves independently of implementations, using semantic versioning (semver 2.0.0). Any third-party implementation may declare CES compliance by passing the CES-TCK.
2. L2 depends only on L0 kernel types (KRN-ALG operator types, KRN-OBS probe types) and the standard library; dependencies on L1/L3–L7 are forbidden.
3. YAML and JSON are both first-class formats: the same document in both encodings must be losslessly interconvertible (round-trip testing is mandatory).
4. Coverage: statements ≥95%, branches ≥85% (CES is held to kernel-layer quality standards).

---

## Module CES-SCHEMA: Specification Schema

### 1. Module Position and Responsibilities

Defines the complete data model of CES documents (Go types), the JSON Schema (for external tooling validation and IDE completion), and field documentation (semantics/type/required/default/constraints for every field). It is the Single Source of Truth of the CES specification: the Go types, the JSON Schema, and the field documentation are kept in sync by a code generator; manual drift is forbidden.

### 2. Package Structure and File Layout

```
ces/schema/
  doc.go           // Package doc: CES specification overview and versioning policy
  experiment.go    // Experiment top-level type (all fields)
  steadystate.go   // SteadyState steady-state hypothesis type
  method.go        // Method perturbation-method type (operator expression)
  probe.go         // Probe type (four kinds)
  rollback.go      // Rollback strategy type
  schedule.go      // Schedule type (once / cron / continuous)
  target.go        // Target type (simulator target / code target)
  meta.go          // Metadata type
  version.go       // APIVersion constants and version negotiation
  gen/             // Code generator: Go types → JSON Schema + field docs
    main.go
  dist/            // Generated artifacts (committed, for external tools)
    ces-v1.schema.json
    fields.md
```

### 3. Core Types and Interfaces (must implement)

- `Experiment` (top level, kind: Experiment):
  - `APIVersion string`: required, format `ces.tencent.com/v1` (v1 to start; major changes require a specification RFC).
  - `Kind string`: required, fixed to `Experiment`.
  - `Metadata Metadata`: `Name` (required, DNS subdomain validation), `Namespace` (default `default`), `Labels map[string]string` (key/value constraint validation), `Annotations map[string]string`.
  - `Spec ExperimentSpec`: required, contains all of the following substructures.
- `ExperimentSpec`:
  - `Target Target`: required. `Kind` (simulator code twin / source code target / external external environment — external is a reserved field in v1 but validation rejects it, to prevent shipping half a feature), `Selector` (target selector: package/function/node/process key-value pairs).
  - `SteadyState []SteadyState`: required, at least 1 entry.
  - `Method Method`: required.
  - `Probes []Probe`: optional (observation probes beyond the steady-state probes).
  - `Rollback Rollback`: required (strategy: auto / manual / timeout; default auto).
  - `Schedule Schedule`: required (once one-shot / cron expression / continuous).
  - `Timeout VirtualDuration`: optional, the experiment's virtual-time budget (inherits the scheduler Budget by default).
  - `Seed uint64`: optional, deterministic seed (generated by the CLI by default and written back into the report).
- `SteadyState`: `ProbeRef string` (references a probe ID), `Expectation Expectation` (value exact value / range interval / predicate predicate expression), `Tolerance Tolerance` (absolute / relative / percent, three types), `HoldFor VirtualDuration` (steady-state hold duration, >0).
- `Method`: `Expression string` (operator algebra expression, supporting ∘ composition, ⊗ concurrent product, p⁻¹ inverse, ε identity, and parenthesized grouping; operands are operator references `operator://<id>` or inline operator definitions), `Operators []OperatorDef` (inline operator definition table).
- `Probe`: `ID string` (unique within the document), `Kind ProbeKind` (http / shell / metric / prom, four kinds), `Spec ProbeSpec` (independent schema per Kind: http has url/method/headers/expect-status; shell has command/timeout/expect-exit-code; metric has query/expect; prom has promql/range/expect), `Interval VirtualDuration` (sampling interval, >0).
- `Rollback`: `Strategy Strategy` (auto/manual/timeout), `Timeout VirtualDuration` (required when strategy=timeout), `VerifySteadyState bool` (whether to re-verify steady state after rollback, default true).
- `Schedule`: `Once *OnceSpec` / `Cron *CronSpec` (five-field cron, virtual timezone) / `Continuous *ContinuousSpec` (Duration required) — exactly one of the three (mutually exclusive).
- `Version`: `Current() string`, `Negotiate(requested string) (string, error)` (version negotiation: supports v1; unknown versions return ErrUnsupportedVersion along with the list of supported versions).

### 4. Key Algorithms and Flows

1. Code generator: parses Go type annotations (struct tags + custom directives) → produces the JSON Schema (draft 2020-12) and the field documentation (fields.md table: field/type/required/default/constraints/example); a CI gate verifies that the generated artifacts match the source (drift ⇒ FAIL).
2. Round-trip guarantee: Experiment → JSON → YAML → JSON → Experiment lossless end to end (unknown-field policy: v1 rejects unknown fields, to prevent typos from being silently swallowed).
3. Versioning policy: APIVersion major changes go through a specification RFC; minor changes only add, never modify or delete; deprecated fields are kept for 2 minor versions and annotated in the documentation.

### 5. Dependencies and Constraints

- Depends on: standard library only (encoding/json, regexp; time only for types, not for runtime) + a YAML parser merged at source level (gopkg.in/yaml.v3, Apache-2.0, vendored under third_party/yaml).
- Depended on by: CES-PARSE (types), CES-VALID (field constraints), CES-TCK (Schema), CTL-CLI (document examples).
- Forbidden: runtime reflection-driven dynamic schema (performance and determinism); any I/O.

### 6. Testing Requirements

- Unit tests: full positive/negative coverage of every type's field constraints (required/format/enum/mutual exclusion); version negotiation (supported/unsupported/empty).
- Round-trip tests: lossless JSON↔YAML conversion (including Chinese characters / special characters / large numbers).
- Generator tests: artifacts compared against hand-written golden files (golden-file testing).
- Fuzz testing: random mutation of valid documents; the parser must not panic (fuzz in CI, 60s fast tier).

### 7. Acceptance Criteria (quantifiable)

1. All type fields consistent across godoc + JSON Schema + fields.md (CI drift check: 0 differences) (design target).
2. Positive/negative field-constraint cases 100% passing; unknown-field rejection cases passing (design target).
3. JSON↔YAML lossless round-trip tests ≥50 sample sets (including boundary characters) 100% passing (design target).
4. Fuzz 60s with no panic (corpus committed).
5. Coverage ≥95%/85%; gates all green (design target).

## Module CES-PARSE: Specification Parsing

### 1. Module Position and Responsibilities

Parses CES documents (YAML/JSON byte streams) into strongly typed Experiments and performs normalization (default filling, reference resolution, expression compilation). The parse output is directly executable (no second pass needed). Parsing is deterministic: the same byte stream yields the same parse result (including error messages).

### 2. Package Structure and File Layout

```
ces/parse/
  parse.go        // Parse main entry: byte stream → Experiment
  normalize.go    // Normalization: default filling / reference resolution / mutual-exclusion checks
  expr.go         // Operator expression lexer and parser (hand-written recursive descent)
  exprcompile.go  // Expression → operator tree (KRN-ALG Operator assembly)
  errors.go       // Structured errors: position (line/column) + field path + rule ID
  parse_test.go
  testdata/       // Valid/invalid sample library (≥100 files)
```

### 3. Core Types and Interfaces (must implement)

- `Parse(data []byte, format Format) (*Experiment, error)`: main entry; format is yaml/json/auto (auto sniffs the first byte: `{` = JSON, otherwise YAML).
- `Normalize(exp *Experiment) (*Experiment, error)`: default filling (Rollback.Strategy=auto, etc.), ProbeRef reference resolution (dangling references are errors), Schedule three-way mutual-exclusion check, Seed default generation (recorded in the return value for write-back).
- `CompileExpr(expr string, ops []OperatorDef) (algebra.Operator, error)`: expression → operator tree. Grammar (EBNF):
  - `expr := term ("∘" term)*`
  - `term := factor ("⊗" factor)*`
  - `factor := "(" expr ")" | operand ["⁻¹"]`
  - `operand := "ε" | operatorRef | inlineDef`
  - `operatorRef := "operator://" id`
- `ParseError`: `Line`, `Column`, `FieldPath` (e.g. spec.steadyState[0].tolerance), `RuleID` (e.g. CES-PARSE-001), `Message`. Error messages are deterministic (map iteration order and pointer addresses are forbidden).

### 4. Key Algorithms and Flows

1. Expression parsing: hand-written recursive descent (yacc generator dependencies are forbidden); operator precedence: ∘ lowest, ⊗ next, ⁻¹ suffix highest; left-associative.
2. Operator tree assembly: operatorRef looks up the Operators definition table (undefined is an error); inline definitions are constructed directly; ε constructs the identity operator; p⁻¹ calls KRN-ALG Inverse (non-invertible operators error here, with the operator ID and position in the error).
3. Error recovery: return on the first error (fail-fast, with full context in the message); no multi-error aggregation (a v1 simplification decision, recorded in ADR-001).
4. Depth protection: expression nesting depth cap of 64 (consistent with KRN-ALG); exceeding it is an error.

### 5. Dependencies and Constraints

- Depends on: CES-SCHEMA (types), KRN-ALG (operator tree assembly), third_party/yaml (merged at source level).
- Depended on by: CES-VALID (validation after normalization), CTL-CLI (entry point).
- Forbidden: any I/O (accepts byte streams only); runtime networking; global state (the parser is reentrant and concurrency-safe).

### 6. Testing Requirements

- Unit tests: full grammar coverage (four operators / parentheses / suffix / references / inline / ε / illegal tokens / depth overflow), ≥3 cases per category.
- Sample-library tests: testdata ≥100 files (60 valid / 40 invalid), all asserting pass/fail and the error RuleID.
- Determinism test: parse the same byte stream 100 times; the serialized output hash is identical (including byte-identical error messages).
- Concurrency test: 100 goroutines parsing different documents concurrently, zero races (-race gate).
- Fuzz testing: random byte streams / truncated documents / over-deep nesting — no panic, no OOM (input cap 10MB; over the cap is rejected).

### 7. Acceptance Criteria (quantifiable)

1. Grammar cases and sample library 100% passing; full RuleID coverage (every error path has a unique RuleID) (design target).
2. Parse determinism: hash-identical across 100 runs; concurrency 100 goroutines with zero -race reports (design target).
3. Fuzz 60s with no panic and no OOM (corpus committed).
4. Parse performance: P99 ≤10ms for a typical 100KB document (benchmark report committed).
5. Coverage ≥95%/85%; gates all green (design target).

## Module CES-VALID: Specification Validation

### 1. Module Position and Responsibilities

Performs semantic-level validation on a normalized Experiment (beyond field formats): steady-state satisfiability, method executability, probe configuration legality, rollback completeness, schedule legality, and target/operator-family matching. Passing validation = the document is executable (runtime no longer fails due to configuration errors).

### 2. Package Structure and File Layout

```
ces/validate/
  validate.go     // Validate main entry: rule-chain orchestration
  rules.go        // Rule registry (unique ID per rule)
  r_steady.go     // Steady-state rule group
  r_method.go     // Method rule group
  r_probe.go      // Probe rule group
  r_rollback.go   // Rollback rule group
  r_schedule.go   // Schedule rule group
  r_target.go     // Target-domain matching rule group
  validate_test.go
```

### 3. Core Types and Interfaces (must implement)

- `Validate(exp *Experiment) ([]Violation, error)`: returns all violations (aggregation mode, complementing PARSE's fail-fast); an exp that is itself invalid (not normalized) returns an error.
- `Violation`: `RuleID string` (e.g. CES-VALID-STEADY-001), `FieldPath string`, `Message string`, `Severity Severity` (error must be fixed / warning recommended to fix).
- Rule registry: `Register(rule)`; each rule implements `Check(exp *Experiment) []Violation`; rule-ID namespaces: the six groups STEADY/METHOD/PROBE/ROLLBACK/SCHEDULE/TARGET.

### 4. Rule List (the first version must implement all of them; no hand-waving allowed)

**Steady-state rule group (STEADY)**:
- CES-VALID-STEADY-001: at least 1 SteadyState.
- CES-VALID-STEADY-002: ProbeRef must point to an existing probe (dangling reference).
- CES-VALID-STEADY-003: HoldFor > 0 and ≥ the probe's Interval (otherwise the steady state can never be satisfied).
- CES-VALID-STEADY-004: Expectation and Tolerance types must match (range expectation paired with absolute tolerance, etc. — type-matrix validation).
- CES-VALID-STEADY-005: predicate expression syntactically valid (compiles).

**Method rule group (METHOD)**:
- CES-VALID-METHOD-001: expression non-empty and compiles (reuses PARSE CompileExpr).
- CES-VALID-METHOD-002: non-invertible operators in the operator tree must declare a compensation strategy explicitly (checks OperatorDef.Compensation).
- CES-VALID-METHOD-003: operator-tree depth ≤64.
- CES-VALID-METHOD-004: the two operators of a concurrent product ⊗ must have disjoint target key sets (reuses KRN-ALG conflict detection).

**Probe rule group (PROBE)**:
- CES-VALID-PROBE-001: ID unique within the document.
- CES-VALID-PROBE-002: Interval > 0.
- CES-VALID-PROBE-003: http-class url must be a reachable target inside the simulator (within the Target.Selector domain; external URLs rejected — the simulator iron rule).
- CES-VALID-PROBE-004: shell-class command forbids commands with real side effects (whitelist validation: the in-simulator shell subset).
- CES-VALID-PROBE-005: expect-status/expect-exit-code/expect value types legal (e.g. HTTP status 100–599).

**Rollback rule group (ROLLBACK)**:
- CES-VALID-ROLLBACK-001: Strategy enum legal (auto/manual/timeout).
- CES-VALID-ROLLBACK-002: when strategy=timeout, Timeout > 0.
- CES-VALID-ROLLBACK-003: when VerifySteadyState=true, the entire steady-state rule group must pass (rollback re-verification depends on a legal steady-state definition).

**Schedule rule group (SCHEDULE)**:
- CES-VALID-SCHEDULE-001: three-way mutual exclusion (exactly one of once/cron/continuous non-empty).
- CES-VALID-SCHEDULE-002: cron has legal five-field syntax and a valid virtual timezone.
- CES-VALID-SCHEDULE-003: continuous.Duration > 0.
- CES-VALID-SCHEDULE-004: once.At is a future virtual time (relative to experiment start).

**Target-domain matching rule group (TARGET)**:
- CES-VALID-TARGET-001: Target.Kind enum legal (simulator/source; external rejected with an "unsupported" hint).
- CES-VALID-TARGET-002: M-family operators must target source (code targets); C-family operators must target simulator (system targets) — operator-family/target-domain matching matrix validation.
- CES-VALID-TARGET-003: Selector non-empty with legal key-value format.
- CES-VALID-TARGET-004: a mixed expression M⊗C requires Target to provide both a source and a simulator selector (dual-target declaration).

### 5. Dependencies and Constraints

- Depends on: CES-SCHEMA (types), CES-PARSE (expression compilation reuse), KRN-ALG (operator-tree checks).
- Depended on by: CTL-CLI (pre-execution validation), CES-TCK (compliance check items).
- Forbidden: any I/O; rule execution order must be deterministic (lexicographic by rule ID, guaranteeing a deterministic violation list).

### 6. Testing Requirements

- Unit tests: ≥1 positive and ≥1 negative case per rule (22 rules ⇒ ≥44 cases); rule-ID uniqueness test.
- Aggregation tests: multi-violation documents return all violations (in deterministic order).
- Determinism test: validate the same document 100 times; the serialized violation-list hash is identical.
- Sample-library reuse: all 40 invalid testdata samples are correctly rejected with matching RuleIDs.

### 7. Acceptance Criteria (quantifiable)

1. All 22 rules implemented; positive/negative cases 100% passing; zero rule-ID conflicts (design target).
2. Violation-list determinism: hash-identical across 100 runs (design target).
3. Validation performance: P99 ≤5ms for a typical 100KB document (benchmark report committed).
4. Coverage ≥95%/85%; gates all green (design target).

## Module CES-TCK: Compatibility Kit

### 1. Module Position and Responsibilities

The CES Technology Compatibility Kit: a third-party implementation may declare "CES compliant" after passing all TCK cases. The TCK is the neutral referee of the open specification: cases are based solely on the specification text, never on Abate implementation details. It is the mechanism that makes the "open specification CES" value pillar real.

### 2. Package Structure and File Layout

```
ces/tck/
  tck.go          // TCK runner: load cases → drive the implementation under test → compare expectations
  case.go         // Case model: input document / expected verdict / expected violation RuleIDs
  driver.go       // Driver interface for implementations under test (third-party adaptation point)
  report.go       // Compliance report generation (pass rate / failure details / compliance-badge decision)
  cases/          // Case library (data-driven, YAML)
    parse/        // Parse cases (≥60)
    validate/     // Validation cases (≥44, one per rule)
    roundtrip/    // Round-trip cases (≥50)
  tck_test.go
```

### 3. Core Types and Interfaces (must implement)

- `Driver` interface (the adaptation point for third-party implementations): `Parse(data []byte, format string) (ParseResult, error)`, `Validate(doc []byte) ([]Violation, error)` — the return structures align with the TCK case model (JSON-neutral format; Go types not required).
- `Runner`: `Run(driver Driver) (Report, error)` — loads all cases → drives them one by one → compares against expectations.
- `Report`: `Total`, `Passed`, `Failed`, `Skipped`, `Details []CaseResult`, `Compliant bool` (Compliant = Failed == 0 and Skipped == 0).
- Case model (YAML): `id` (TCK-PARSE-001 format), `input` (document bytes), `expect` (accept/reject + RuleID list + specification-clause references).

### 4. Key Algorithms and Flows

1. Data-driven cases: cases are data (YAML); adding a case requires zero code; case IDs cross-reference specification clause numbers (every case must cite a specification text section).
2. Neutral comparison: expected output is a JSON-neutral description (accept/reject + violation RuleID set); implementation-internal structures are not compared.
3. Compliance decision: Compliant only when everything passes; partial passes print failure details (case ID + expected vs actual + specification clause reference).
4. Versioning policy: with a specification minor version the TCK only gains cases; a major version gets its own TCK (tck-v1/tck-v2 coexist).

### 5. Dependencies and Constraints

- Depends on: CES-SCHEMA (specification clauses cited by cases), standard library.
- Depended on by: external third-party implementations (via the Driver adapter); XCU-REL (TCK shipped with releases).
- Forbidden: cases depending on Abate private behavior (case-review checklist: every case's expectation must be derivable from the specification text).

### 6. Testing Requirements

- Bootstrap test: Abate's own implementation (CES-PARSE/CES-VALID) runs the TCK as the first Driver and must pass 100% (eating one's own dog food) (design target).
- Case-quality tests: every case cites a specification clause (scan-verified); case-ID uniqueness.
- Neutrality test: construct a minimal third-party reference implementation (test fixture) that passes the TCK (proving the TCK is not bound to Abate private behavior).

### 7. Acceptance Criteria (quantifiable)

1. Case library ≥154 cases (parse ≥60 + validate ≥44 + roundtrip ≥50), all with specification-clause references (design target).
2. Abate's own Driver pass rate 100% (resident in CI) (design target).
3. The minimal reference-implementation fixture passes the TCK (neutrality proof, report committed).
4. TCK runner's own coverage ≥95%/85%; gates all green (design target).
